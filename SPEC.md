# Clod-key-proxy — спецификация UI и журнал замечаний

## Назначение

`Clod-key-proxy` разделяет два независимых контура:

1. **Claude CLI** — профили и запись только в `~/.claude/settings.json`.
2. **Zoo Bridge** — отдельное окно управления локальным мостом из `app-next/bridge` на `127.0.0.1:33110`; ключ и upstream хранятся только в `app-next/bridge/.env`.

Главная форма не должна содержать карточку статуса Bridge или встроенные Start/Stop-контролы.

## Актуальное состояние

- Главная форма открывает отдельное окно Bridge отдельной кнопкой и через пункт трея.
- В окне Bridge есть Start, Stop, Restart и действие загрузки текущего профиля.
- Закрытие окна Bridge не должно останавливать процесс моста: разрешено только скрыть окно и остановить его UI-таймер.

## Реестр косметических и UX-дефектов

### BUI-01 — нет явной кнопки закрытия окна Bridge

**Статус:** исправлено (2026-09-11). Видимая кнопка `✕` в шапке окна Bridge ([`ClodKeyProxy.ps1`](app-next/ClodKeyProxy.ps1:1925)); закрытие скрывает окно и останавливает только его таймер, порт `33110` продолжает слушать. Покрыто самопроверкой `bridge window close button missing`.

Окно Bridge должно содержать видимую кнопку `✕` в шапке, аналогичную закрытию окна журнала. Кнопка обязана скрывать окно и останавливать только его таймер обновления; Bridge-процесс на `33110` не останавливается.

**Критерии приёмки:**

- видимая кнопка закрытия находится в шапке;
- нажатие скрывает окно без ошибки;
- окно можно снова открыть через главную форму и трей;
- порт `33110` продолжает слушать после закрытия окна.

### BUI-06 — дизайнерское tray-меню с анимацией (не стандартный ContextMenuStrip)

**Статус:** исправлено (2026-09-11). Меню трея перекрашено кастомным `ClodUi.MenuRenderer` (наследник `ToolStripProfessionalRenderer`) + `ClodUi.MenuColorTable` ([`ClodKeyProxy.ps1`](app-next/ClodKeyProxy.ps1:483)): скруглённые hover-пилюли, тема из палитры, свои разделители/рамка, повторная окраска в `Apply-Theme`. Анимация «zoom из трея» — `DrawAnimatedRects` (`IDANI_CAPTION`, `Shell_TrayWnd`→`TrayNotifyWnd`) в `ClodNative.AnimateFromTray` ([`ClodKeyProxy.ps1`](app-next/ClodKeyProxy.ps1:96)), вызывается после `Show()` во `Show-Main`. Код C# переписан под CodeDom C#5 (без expression-bodied) под PowerShell 5.1.

**Разведка через веб (Playwright, Google, проверено 2026-09-11):**

- Подтверждено на Stack Overflow / Microsoft Learn: «кастомное тёмное скруглённое контекстное меню в WinForms = `ProfessionalColorTable` + `ToolStripProfessionalRenderer` + нативный трюк для скруглённых углов окна меню» (сниппет из выдачи: «DarkRoundedRenderer: Extends ToolStripProfessionalRenderer using the custom color table, handles anti-aliased rounded item backgrounds in OnRenderMenuItemBackground, enforces white/gray text colors»).
- Подтверждён нативный Win32-паттерн анимации меню/окна из трея: **`DrawAnimatedRects`** (user32, `IDANI_CAPTION`) — рисует «zoom»-переход между прямоугольником трея (`TrayNotifyWnd` через `FindWindow("Shell_TrayWnd")` → `FindWindowEx(..., "TrayNotifyWnd")` → `GetWindowRect`) и прямоугольником окна/меню. Полный рабочий C#-пример найден в выдаче: анимация выполняется ДО `this.Hide()` (сворачивание) и ПОСЛЕ `this.Show()` (восстановление), DWM-оптимизировано, классический эффект Windows. Это стандарт для «меню выезжает из трея».
- Важно из выдачи: флаг `SPI_SETMENUANIMATION` — системная анимация меню должна быть включена, иначе `DrawAnimatedRects` для меню игнорируется (для собственной формы это не требуется).
- Ссылки-источники из выдачи: Stack Overflow «Windows 10 Styled ContextMenuStrip» (2015, актуальный подход), Microsoft Learn `ToolStripProfessionalRenderer Class`, Stack Overflow «Animate the Window movements from tray» (`DrawAnimatedRects` как лучший ответ).

**Статус:** открыт.

Текущее меню трея — стандартный `Windows.Forms.ContextMenuStrip` ([`ClodKeyProxy.ps1:2104`](app-next/ClodKeyProxy.ps1:2104)): системная серая палитра, стандартный шрифт, нулевая анимация. Требование: меню должно быть в дизайн-языке приложения (soft-neumorphic, тёмная/светлая тема, свои шрифты) и открываться с анимацией.

**Разведка — проверенные приёмы «красивого» tray-меню в WinForms:**

1. **Кастомный ToolStripRenderer** — самый чистый способ перекрасить `ContextMenuStrip` без переписывания: наследник `ToolStripProfessionalRenderer` с переопределёнными `OnRenderToolStripBackground`, `OnRenderMenuItemBackground`, `OnRenderToolStripBorder` рисует rounded-панель цвета `$script:surface`, hover-строку акцентом, разделители тонкой линией. Используется в SyncTrayzor, Everything, ModernFlyouts. Плюс: сохраняется вся механика меню (клавиатура, чекбоксы, sub-menu).
2. **Полностью owner-drawn флаут-меню** — вместо `ContextMenuStrip` показывается наша же borderless `ClodForm` со списком `ClodButton`, позиционируется над треем (`Screen.PrimaryScreen.WorkingArea`, координаты `Cursor.Position`). Так делают PowerToys-модули и Rainmeter-гаджеты: полный контроль скруглений, теней, шрифтов, иконок. Минус: нужно вручную закрывать по клику вне (deactivate/capture) и по Esc.
3. **Анимация открытия** — три проверенных варианта:
   - **slide-up + fade** (как у нашего флаута): форма меню появляется на 8–12 px ниже и `Opacity=0.25`, за 120–160 мс поднимается и проявляется — тот же `AnimTimer`-паттерн;
   - **scale-in**: панель меню рисуется с `Pulse`/растущим радиусом (у нас есть `ClodStatusCard.Pulse`) — «надувается» из точки трея;
   - **stagger**: строки меню проявляются последовательно с шагом 20–30 мс — эффект «каскада», стандарт в Fluent-меню.
4. **Hover-эффекты строк** — заливка акцентом с плавным интерполятором (`Shape.Mix` уже есть в C#-хелперах), лёгкий inset для нажатой строки — согласуется с неоморфизмом кнопок.
5. **Иконки в строках** — монохромные глифы тем же шрифтом `$fontGlyph` (уже есть: ☰, ☕, ☀) вместо системных изображений.
6. **Чего избегать:** `ToolStripProfessionalRenderer.RenderMode.System`, системный синий highlight, шрифт по умолчанию, резкое появление без анимации, белые вспышки при первом открытии (лечится `menu.BackColor` до показа).

**Рекомендация:** вариант 1 (renderer) + анимация 3a (slide-up + fade) как минимальный надёжный шаг; при желании — переход на вариант 2 (owner-drawn флаут-меню) со stagger-анимацией как финальная цель. Renderer можно применить к существующему меню без изменения структуры `Build-TrayMenu`.

**Критерии приёмки:**

- меню визуально совпадает с темой приложения в светлой и тёмной палитре;
- открытие анимировано (≤180 мс), без мерцания и системных вспышек;
- hover строки — акцент с плавной интерполяцией; шрифт и глифы — фирменные;
- клавиатурная навигация и Esc сохраняются (при варианте 1 — бесплатно);
- пункт «Bridge» визуально выделен (глиф моста) и открывает флаут на странице Bridge (BUI-05).

### BUI-05 — окно Bridge как вторая страница флаута, не отдельное окно по центру

**Статус:** частично исправлено (2026-09-11). Окно Bridge больше НЕ открывается по центру: заякорено к углу трея через `Position-Flyout-For` ([`ClodKeyProxy.ps1`](app-next/ClodKeyProxy.ps1:1946)), `ShowInTaskbar=$false` (нет второй иконки в таскбаре) и открывается с анимацией slide-up+fade отдельным таймером `BridgeAnimTimer`, не связанным с анимацией CLI-флаута. Полный panel-swap внутри одной borderless-формы осознанно отложен: он конфликтует с инвариантом T-02.1 и самопроверкой «главная форма не содержит окно Bridge».

Сейчас окно Bridge открывается как независимое окно по центру экрана. Требование: Bridge должен выглядеть и вести себя как **вторая страница того же флаута ClodKey**, что anchored к трею, а не как плавающее окно Windows.

**Разведка (проверенные практики tray-приложений WinForms):**

1. **Panel-swap, а не второй Form** — эталонный приём для «страниц» в borderless tray-flyout: обе страницы — `Panel` внутри одной borderless формы; переключение = `page1.Visible=false; page2.Visible=true` + пересчёт `ClientSize`. Так делают попапы (Rainmeter-скины, PowerToys Run, Dropbox flyout). Плюс: нет второй иконки в taskbar, нет проблем с Z-order, общая тема применяется один раз.
2. **Slide-переход** — горизонтальный сдвиг контента (или fade через `Opacity` дочерней панели) на 120–180 мс; в WinForms делается тем же `Windows.Forms.Timer`, который уже есть у флаута (`AnimTimer`, slide-up + fade). Второй таймер не нужен.
3. **Индикатор страницы в шапке** — точка/сегмент «1·2» или таб-глифы в header row; клик по глифу Bridge в шапке = переход на страницу 2. Это стандарт для многостраничных flyout (см. tray-попапы 1Password, SyncTrayzor).
4. **Tray menu с анимацией** — пункт меню «Bridge» открывает флаут СРАЗУ на странице 2: `Show-Main(page:2)`. Анимация slide-up остаётся той же; опционально короткий fade-in страницы 2 (120 мс) как акцент. Прямой показ отдельного окна из меню трея — анти-паттерн (окно теряет anchor, появляется в центре, ломает ментальную модель «флаут из трея»).
5. **Размер страницы** — страница Bridge может быть выше страницы 1; `ClientSize` пересчитывается при переключении (как уже делает `Do-Layout`), флаут остаётся anchored к трею (`Position-Flyout`).
6. **Чего избегать:** `ShowDialog()`, `TopMost` отдельного окна, второй `NotifyIcon`, `FormBorderStyle` отличный от None для страницы — всё это ломает «один флаут» инвариант.

**Критерии приёмки:**

- Bridge-страница открывается внутри того же borderless флаута, anchored к трею;
- переключение страниц — анимированное (slide/fade ≤200 мс), без второго окна в taskbar;
- пункт трея «Bridge» открывает флаут сразу на странице Bridge;
- тема, шрифты, палитра — общие с страницей 1, применяются одним `Apply-Theme`;
- закрытие/сворачивание флаута на странице Bridge ведёт себя идентично странице 1 (hide to tray);
- существующие контролы Bridge (Start/Stop/Restart/Load/мини-лог/закрытие) сохраняют семантику.

**Критерии приёмки:**

- значение `on`, `off` или `n/a` соответствует доступным данным;
- все пользовательские подписи локализованы для RU/EN/ZH/ES.

### CTX-01 — 413 `context_limit` из-за одного гигантского tool result

**Статус:** исправлено (2026-09-11).

**Замер:** [`proxy.log`](app-next/bridge/proxy.log:229) — сессия `~201698 est. tokens` с одним tool result ~774 235 символов (~193k токенов) получала постоянный `413 context_limit` на всех повторах, потому что tool result считался неделимым.

**Решение:**

- пара `tool_use`/`tool_result` сохраняется всегда, но payload tool result ограничивается `COMPACT_MAX_TOOL_RESULT_TOKENS` (по умолчанию `24000` токенов) с сохранной обрезкой head+tail и явной пометкой `[bridge] ... tool result clipped to fit context`;
- новая функция [`clipOversizedToolResults()`](app-next/bridge/server.mjs:646) вызывается в [`compactConversation()`](app-next/bridge/server.mjs:696) до общего планировщика;
- параметр виден в `/health` как `compact.maxToolResultTokens`;
- `NO_STREAM_MODELS` очищен: пустое значение означает настоящий прогрессивный upstream SSE для всех моделей — обёртка в один синтетический чанк только по явному opt-out оператора.

**Проверка:** `npm run test` → `ALL GREEN: 107 passed, 0 failed` (включая новый тест `oversized tool result is clipped but remains paired`); `/health` возвращает `maxToolResultTokens=24000`; Bridge перезапущен и слушает `33110`.

### CTX-02 — 413 `context_limit` из-за суммы защищённого хвоста

**Статус:** исправлено (2026-09-11).

**Замер:** [`proxy.log`](app-next/bridge/proxy.log:348) — сессия ~202921 est. tokens: первый проход обрезал tool result'ы по потолку 24000, но сумма хвоста из нескольких защищённых циклов (каждый почти у потолка) + system + head превышала бюджет 180000 — 413 на каждом повторе.

**Решение:** итеративный второй проход в [`compactConversation()`](app-next/bridge/server.mjs:793): потолок одного tool result сужается вдвое (24000→12000→6000→3000, минимум 2000, до 8 проходов), пока суммарный объём не влезет в бюджет. Пара `tool_use`/`tool_result` сохраняется всегда.

### CTX-03 — счётчик контекста Zoo скачет (500 ↔ 58000)

**Статус:** реализовано (V1, 2026-09-11). Мост — источник правды о контексте: `usage.prompt_tokens` во всех путях (антропик-стрим `writeUsage`, OpenAI-стрим `emitFilteredSseStream`/`emitFilteredSse` через `calibrateSseLine`, обёрнутый `emitSse`, нестримовый `emitJson`) подменяется калиброванной оценкой `after` пост-компакции ([`server.mjs`](app-next/bridge/server.mjs:551) `calibrateContextUsage`/`applyCalibratedUsage`). Коэффициент — EMA по правдоподобным значениям провайдера (отклонение ≤ ±50%); мусорные cache-hit числа в показ не попадают. Сырой `USAGE in=...` остаётся в логе. `npm run test` зелёный.

### CTX-04 — 413 `context_limit` из-за гигантской реплики БЛОЧНОГО формата в последнем user-ходе

**Статус:** исправлено (2026-09-11).

**Замер:** [`proxy.log`](app-next/bridge/proxy.log:762) — сессия `~240074 est. tokens`, роли `...a,t,u`, кит на 936140 знаков лежит в ПОСЛЕДНЕЙ user-реплике блочного формата (`content:[{type:'text',text:...}]`). `clipOversizedToolResults` трогает только `role==='tool'`, а `clipOversizedTurns` фильтровал `typeof m.content === 'string'` → блочный user-ход оставался неделимым → 413 на каждом повторе.

**Решение:** [`clipOversizedTurns()`](app-next/bridge/server.mjs:749) теперь принимает и `Array.isArray(m.content)`: считает длину по text-блокам и стрижёт каждый блок, превышающий лимит, через `clipTextMiddle`. Бюджетная проверка идёт после `enforceToolResultBudget`, так что гигантский user-блок в защищённом хвосте теперь стрижётся.

**Проверка:** реплей на точной живой форме (кит в последнем user-блоке + кит в tool-блоке) → [`REPLAY OK`](.replay-413.mjs): `BEFORE 494500 → AFTER 50270`, обе реплики подстрижены, ошибок нет; `npm run test` → `ALL GREEN: 107 passed, 0 failed`; Bridge перезапущен, `/health` 200.

**Замер:** [`proxy.log`](app-next/bridge/proxy.log:534) — при монотонном росте тела запроса (332k→390k байт, msgs 114→144) провайдер возвращает `input_tokens`: 57442 → 375 → 1039 → 2153 → 454 → 1532 → ... Значение 375 при 337k байт физически невозможно для полного промпта — провайдер отдаёт кэш-хиты/оценки вместо реального подсчёта.

**Корень:** agentrouter не гарантирует корректный `usage.input_tokens`; мост честно транслирует мусор, Zoo показывает скачки.

**Согласованное решение (V1) — «мост — источник правды о контексте»:**

1. Мост знает оба числа: `before` (оценка сырого запроса Zoo, `conversationTokens()` до компакции) и `after` (оценка реально ушедшего провайдеру, после компакции — уже пишется в `COMPACT ... -> ~137309`).
2. В финальном usage-чанке стрима и в JSON-ответе `usage.prompt_tokens` подменяется на калиброванную оценку `after` — счётчик Zoo показывает фактический контекст модели, а не сырую историю Zoo.
3. Момент сжатия виден в Zoo как естественное падение счётчика (ожидаемое поведение, как у Claude Code auto-compact).
4. Калибровка без внешних вызовов: мост копит отношение `upstream_in / after` только по правдоподобным значениям upstream (отклонение от оценки не более ±50%); коэффициент применяется к `after`. Мусорные значения (375 при 337k байт) в калибровку и показ не попадают.
5. Ноль дополнительных запросов к провайдеру — оценка бесплатна.

**Критерии приёмки:**

- счётчик Zoo монотонен в пределах одной сессии между компакциями;
- после компакции счётчик падает до оценки `after`;
- `USAGE in=...` в логе сохраняется как сырой факт провайдера (диагностика);
- `npm run test` остаётся зелёным; старый мост 33009 не затрагивается.

### CTX-05 — 413 `context_limit` из-за НЕ-текстового блока (картинка/структура) в ходе

**Статус:** исправлено (2026-09-11). Это был настоящий корень «бесконечной игры в догонялки».

**Замер:** [`proxy.log`](app-next/bridge/proxy.log) — живой сбой `~240076 est. tokens` повторялся даже после того, как процесс моста уже содержал блоковый фикс CTX-04.

**Корень (расхождение метрик):** [`messageTokens()`](app-next/bridge/server.mjs:542) измеряет блоковое сообщение как `estimateTokens(JSON.stringify(content))` — то есть считает **все** блоки, включая base64-картинки и любые не-текстовые payload'ы. А [`clipOversizedTurns()`](app-next/bridge/server.mjs:749) мерил и стриг только `b.text`. User-ход, объём которого в НЕ-текстовом блоке (вставленная картинка, структурированный payload), выглядел для стрижки маленьким, но оставался огромным для бюджета → никогда не стригся → вечный `context_limit`. Текстовые реплеи проходили (у меня кит был строкой/текст-блоком), живой падал — отсюда ощущение «чиню, а ошибка та же».

**Решение:**
- [`clipOversizedTurns()`](app-next/bridge/server.mjs:749) теперь меряет блоковый ход по тому же JSON-метрику (`estimateTokens*4`) и стригёт только text-блоки, сохраняя картинки (инвариант «изображения не исчезают молча»).
- Новая [`collapseNonTextPass()`](app-next/bridge/server.mjs:798) — финальный проход, подключаемый в [`compactConversation()`](app-next/bridge/server.mjs:951) только когда текстовой стрижки не хватило: схлопывает не-текстовые блоки в маркеры от самого большого, пока бюджет не сойдётся. Маленькие картинки при этом сохраняются.
- Текст ошибки `context_limit` теперь сам перечисляет 3 самых больших выживших сообщения (`[largest: #N role(block)~tok]`) — будущий сбой само-описывающийся, без гадания о форме.

**Проверка:** детерминированный реплей image-блока [`.replay-img.mjs`](.replay-img.mjs) → `IMG REPLAY OK` (последний user-ход 225033→32 эст. токенов, без ошибки); [`REPLAY OK`](.replay-413.mjs) на текстовом блоке; `npm run test` → `ALL GREEN: 107 passed` (включая сохранность картинок); **живой end-to-end** [`.live-413.mjs`](.live-413.mjs) на новом процессе моста → запрос дошёл до upstream (`HTTP 402 quota`), `context_limit` НЕ возвращён.

### CTX-06 — отключение передачи изображений (решение «кодер забыл контекст»)

**Статус:** реализовано (2026-09-11).

**Симптом:** [`proxy.log`](app-next/bridge/proxy.log) — `COMPACT hybrid: ~348843 -> ~6204 est. tokens (msgs 221 -> 16)`: мост выкидывал ~200 реальных сообщений, потому что одна вставленная картинка (~936k base64 ≈ 234k токенов) раздувала `before` выше бюджета 180k, и drop-цикл жертвовал историей. Модель оставалась почти без контекста → «кодер забыл сессию».

**Решение (по команде оператора):** передача изображений отключена полностью. [`stripImages()`](app-next/bridge/server.mjs:452) вырезает все image-блоки (`image` и `image_url`, base64 и url) из **входящих** запросов в [`proxy()`](app-next/bridge/server.mjs:1849) ДО компакции и ДО обращения к upstream; каждый заменён текстовым маркером `[bridge] image attachment removed`. `rawBody`/`shape` пересчитываются, поэтому бюджет, лестница восстановления и логи видят уже очищенный запрос. Флаг `STRIP_IMAGES` (default `1`), виден в `/health` как `stripImages`.

**Почему на границе, а не в компакции:** компакция не тронута → тесты сохранности картинок (`image payload survives compaction byte-identical`, `image block still typed image_url`) остаются зелёными; base64 физически не попадает ни в бюджет, ни к модели, ни в diag-дампы.

**Проверка:** `npm run test` → `ALL GREEN: 107 passed`; живой [`.live-stripimg.mjs`](../Clod-key-proxy/.live-stripimg.mjs) (запрос с big-картинкой + 80 реплик) → `HTTP 200`, `STRIP IMAGES: removed 1 image block(s)`, `COMPACT line: none` (диалог влез без массового удаления). `/health` отдаёт `stripImages:true`.
